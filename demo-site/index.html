Five sequence architectures, implemented from first principles and measured

Pure-PyTorch implementations of S4D, Mamba, Mamba-2, Mamba-3 (complex) and a Transformer baseline. Equivalence tests compare alternative computation paths (for example S4D's FFT convolution against its step recurrence), but the original tests missed two bugs, now fixed and covered by reference tests, that affect every committed S4D, Mamba-2 and Mamba-3 number. Every number below is a committed measurement, not a paper claim.

These results are stale. Capability: where each architecture wins

Cumulative parity needs the state to rotate in response to each input. Of these models only Mamba-3 has input-dependent complex transitions, and only Mamba-3 clearly beat chance (one seed, no ablation that switches the rotation off). Selective copying rewards gating: the LTI S4D failed it, but every score comes from a test that is longer and has more pairs than training. Exact copying at the trained length of 32 was solved by the Transformer and by the LTI S4D, while Mamba-1/2 were still improving when training stopped, so it does not show that attention is required.

Selective copying

Marker-value pairs in noise; train L=64 (3 to 5 pairs), test L=128 (5 to 10 pairs), so every score is out of distribution and no in-distribution score was recorded. Mamba-1/2 token accuracy is close to what a model would get by copying only the first five values, the most it saw in training, so it may not show generalization to more pairs. Two bars per model: full-sequence success and token accuracy. Mamba-3's low score is reported as measured (one seed).

Exact copying (in-distribution L=32)

Reproduce a 32-token string (task adapted from Jelassi et al., ICML 2024). Training always used length 32, so the answer is a fixed shift of the prompt, which the LTI S4D also learned perfectly. Mamba-1/2 did not learn it within 6 epochs and were still improving, and every model, the Transformer included, scored 0 at lengths 64 and 128. This is not a clean reproduction of the paper's Transformer-vs-SSM gap.

Decode cost per token (ms)

The lines measure different things. S4D and Mamba-1: true stepwise decode with an O(1) state (S4D's pre-fix step() also recomputed its discretization every token, which inflates its cost). Transformer, Mamba-2 and Mamba-3: one forward pass over the whole sequence divided by T (prefill / T), not a per-token decode cost. The Transformer has no KV cache, so each new token would need a full forward pass over the prefix; the plotted 0.0015 to 0.0107 ms are not that cost, and its low line does not make it the cheapest decoder.

How was this measured?

The benchmark is an experiment, not a stopwatch screenshot. Step through the actual protocol implemented in benchmarks/efficiency.py: measured methodology

  • Equivalence tests compare alternative computation paths: S4D's FFT convolution against its step recurrence, Mamba-2's chunked scan against its sequential scan, Mamba-1's step() against its forward pass, and Mamba-3 against the Mamba-1/2 update when λ=1 and the rotation frequency is zero. The original tests passed on code with two bugs behind every committed S4D, Mamba-2 and Mamba-3 result (S4D's discretized input matrix was off by a factor of ΔA, and Mamba-2/3 heads did not each receive their group's full B and C), because each comparison shared the faulty step or bypassed it, and the S4D test never reached the multi-chunk kernel used above 1024 tokens. Both bugs are fixed, and reference tests added with the fixes check S4D against a closed-form discretization and across kernel chunks, and the Mamba-2 and Mamba-3 blocks against naive per-head references. The committed results were not regenerated. Run: python -m pytest tests/ -q
  • Every figure on this page regenerates from committed JSON: results/*.json, python demo-site/build.py.
  • Theoretical O(T) and wall-clock are different claims; the python-loop scans are O(T) in operations but 10 to 100× slower in wall-clock - exactly why fused kernels and Mamba-2's matmul form exist.
